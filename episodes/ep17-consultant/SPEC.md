# EP17 施工規格

本規格整理自《網頁設計》第 17 講第 5.1 節的需求；是學員審閱與實作依據。

## 網站目標

讓客戶能理解顧問方案、預約時段、付款流程、付款成功/失敗頁與交付邊界。

## 必要區塊

1. 首頁：顧問定位、適合客戶、預約諮詢按鈕
2. 服務方案：方案名稱、價格、時長、交付物、不包含項目
3. 案例與文章：案例摘要、方法論文章、可驗證成果
4. 預約表單：公司類型、問題描述、預算、可預約時段
5. 訂單摘要：方案、金額、稅額、總額、預約時間、退款規則
6. 付款流程示意：前往付款、付款中、付款成功、付款失敗、使用者取消
7. 交付說明：會議連結、會前資料、交付物、後續追蹤

## 資料模型

請示範以下六張表，並用外鍵 id 串接（對應第 4 節表 17-2）：
- ConsultingPackage(id, 名稱, 價格, 時長, 交付物, 不包含項目)
- ConsultationBooking(id, 客戶, 方案 id, 預約時間, 需求摘要, 狀態)
- Order(id, 預約 id, 金額, 稅額, 總額, 狀態)
- PaymentTransaction(id, 訂單 id, 金流商, 交易編號, 付款狀態, 回傳時間)
- PaymentCallback(交易編號, 原始回傳資料, 驗證結果, 處理時間)
- DeliveryRecord(預約 id, 會議連結, 交付物, 完成狀態, 後續事項)

## 互動示意

用少量 JavaScript示範：選擇不同方案會改變訂單金額；點擊付款按鈕後進入付款中狀態；可切換顯示付款成功、付款失敗、使用者取消三種結果；成功後顯示下一步交付說明。

## 技術補充

請在頁面中補一張「原型 / sandbox / 正式環境」差異表。內容要包含：是否使用真實商家帳號、是否需要後端、是否驗證 webhook 簽章、是否可以收真實信用卡、是否處理發票與退款。

## 設計要求

請做成一個可以直接打開的單一 index.html 檔案（HTML、CSS 寫在同一個檔案內），使用 RWD。畫面要清楚標示這是金流流程原型，尚未真正串接藍新或綠界。不要把商店代號、API 金鑰或交易簽章寫在前端。不要承諾保證成效、保證營收倍增或不可能驗證的結果。


## 課堂定稿補充

### 六張資料表，撐起從預約到交付的金流閉環

這裡把一筆顧問服務拆成六張資料表，先用中文理解它們各管什麼。ConsultingPackage 是顧問方案，ConsultationBooking 是預約紀錄，Order 是訂單，PaymentTransaction 是付款交易，PaymentCallback 是付款通知紀錄，DeliveryRecord 是交付紀錄。欄位中的 id，就是用來識別某一筆資料的編號。訂單摘要要同時讀取方案、預約與訂單，才知道客戶買什麼、何時會面、付多少錢。每張表的欄位都有用途，下一步再用識別編號把它們串起來。

### 外鍵把六張表串成一條不留斷點的閉環

外鍵是一張表用欄位指向另一張表的某一筆。請逐段核對關聯：預約找方案，訂單找預約，交易找訂單，回呼找交易，交付找預約。若只收到付款通知，卻找不到對應交易與訂單，就無法把結果寫回同一筆生意；因此要用外鍵串通資料。

### 預約時段互動：已約不可選，一次只選一格

這段 JavaScript 是讓網頁回應點選的互動程式。我們先看三個結果：已約時段點不下去，一次只會選一個時段，選到的編號能被記住。booked 是已約標記，selected 是目前選取的標記；forEach 是逐個處理，classList 管理這些標記，return 代表停止這次操作。contains 是檢查有沒有標記，remove 和 add 是移除與加入，dataset.id 是這個元素帶的時段編號。程式先檢查已約，再移除舊選取、加上新選取。booking.slotId 先記住時段編號，送出後由後端寫入預約紀錄。實際點一個已約時段，再連續換兩個可用時段，核對畫面和記住的編號，就知道 AI 做的互動是否對得上需求。

### 圖17-1｜訂單狀態的流轉與分支

訂單狀態機的核心是在什麼狀態、收到什麼事件、轉到什麼狀態。主線是草稿送出訂單後變成待付款，付款成功通知驗證通過變成已付款，排定會議後變成已排程，交付完成後變成已完成。這條主線之外有三個分支：待付款收到 驗證後確認付款失敗會變成付款失敗，付款失敗可以重新發起付款、回到待付款再試一次；待付款如果使用者主動取消，會變成已取消；已付款之後，退款完成才變成已退款。付款失敗與取消都是從待付款岔出，但只有付款失敗能回頭再試，退款只發生在已付款之後，這兩條分支不能混為一談。 這裡的驗證包含確認付款成功、訂單與金額一致；收到通知或簽章正確，都不能單獨當作付款成功。 付款失敗回待付款是訂單轉移。重試時的交易處理方式，須依金流商規則設計。

### 付款狀態：五個狀態與分支

付款與訂單分開記。客戶按前往付款，由後端建立交易；金流回傳成功後，後端還要驗證簽章、訂單與金額，才能確認付款結果。失敗與取消仍是付款中的分支。前台不能靠成功頁把訂單改成已付款，後台也不能因通知重送就再交付一次。 付款成功、付款失敗、使用者取消這三種結果記在 PaymentTransaction；Order 只依後端驗證的結果更新自己的狀態。

### 真實金流串接的五個責任點

網站須從建立訂單到完成交付跑通全程，依五個責任點逐項驗收：建立訂單時，方案、金額、稅額、預約時間、退款規則要先固定，金額不能在付款後才被前端任意修改；建立交易時，商店代號留在後端設定。Hash Key 是金流驗證用的密鑰，Hash IV 是搭配算法的初始值；API 金鑰像系統介面的通行密碼，這些機密都由後端保管；回到網站這一步，成功頁只是體驗提示，不是收款憑證；Webhook 驗證這一步，真正更新訂單狀態的是後端驗證後的通知；最後交付與紀錄，付款不是結束，付款後的交付才是商業閉環的終點。金流閉環也包括開立發票的流程。

### 原型、沙盒測試、正式營運：三種環境

三種環境使用不同帳號和資料。原型先用模擬交易呈現畫面與流程。sandbox 就是沙盒測試環境，用金流商的測試商店、測試卡號與測試資料，把付款流程跑一遍。production 就是正式營運環境，使用實際商家的金流帳號與正式網址。後端環境變數是伺服器上的設定值，用來分開各環境的帳號與機密設定；還要接上交易簽章、金流主動通知驗證、發票與退款流程。每往下一層，就核對這一層真的完成了哪些設定與測試，把結果寫回交付清單。
