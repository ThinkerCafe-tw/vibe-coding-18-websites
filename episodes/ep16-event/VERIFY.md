# EP16 驗收清單

## 逐項檢查

AI 產出後不要只看第一眼漂不漂亮，請依序檢查：

- [ ] 首頁第一屏說清楚服務適合誰、下一步是什麼。
- [ ] 資料欄位足以支撐核心流程，而非只留姓名電話。
- [ ] 票種有價格、名額、開賣與截止時間。
- [ ] 售完後進入候補，而非繼續顯示可報名。
- [ ] 付款逾時、取消、退款與報到狀態分得清楚。
- [ ] 通知含報名成功、付款提醒、活動前提醒、候補通知與異動通知。
- [ ] 個資同意把必要通知與行銷授權分開。
- [ ] 價格、限制、取消或隱私規則清楚。
- [ ] 手機版能完成主要行動，且文字與按鈕不重疊。

## 主動測試

本講是**最高風險、會扣到錢的票務站**，名額、候補、付款任一件靜默失敗，都是收錢沒位子或重複扣款的真實糾紛。最招牌的一測：把某票種名額調到剩 1 個，連送兩筆報名，看第二筆是被擋下轉候補，還是名額扣成 −1 照樣收。

記住：**AI 是被告不是法官，畫面才是證據**，它說「擋好了」不算數。

## 課堂定稿補充

### 招牌驗收：最後名額的占位測試

把票種名額調到剩一，用兩個獨立請求同時送出報名。預期一筆占位成功，另一筆不得占位。核對 TicketType 的名額、Registration 的報名與 WaitlistEntry 的候補紀錄，確認三份紀錄和畫面一致。占到名額仍可能是待付款。

### 把規格交給 AI，再親手驗收

把前面的需求整理成提示詞：活動資訊、票種、報名流程、候補規則、通知說明與八類資料欄位。JavaScript 負責選票種換總價等互動，CSS 是控制網頁排版的樣式。產出後先看票種的價格、名額、開賣與截止時間，再看售完後的新報名有沒有依規則進候補。付款逾時、取消或退款、報到各有紀錄，六種通知逐一核對，必要通知與行銷授權分開。最後縮窄畫面：平板改兩欄，手機改一欄，頁首上下排列，按鈕整排可點。程式裡的 media query，就是依畫面寬度切換樣式；max-width 是套用的寬度上限，程式的 px 就是像素，這裡用來計算網頁寬度；課本用一千零二十四個像素與六百四十個像素兩段。先核對看到的結果，再對照程式，發現缺口就請 AI 改那一點，修完重新操作一次。規格寫清楚，交給 AI 做，最後一定要自己親手點過一次。



## 資料一致性主動回驗

- [ ] 基準日的一般票應標示尚未開賣，票卡與選單停用；嘗試送出仍不建立報名，剩餘保持 12。
- [ ] 早鳥最後一名送出後才扣成 0、顯示已售完並開放候補；測試開賣前、開賣當刻、截止當刻與截止後的狀態邊界。


## 多筆資料與操作一致性回驗

- [ ] 分別做未付款取消、保留逾時與付款後取消；前兩者沒有退款紀錄，已付款取消保留原收款明細與時間，重新整理仍一致。

## 多筆報名狀態回驗

- [ ] 第一位選學生票，完成付款及確認；不重設再新增第二位，控制台應自動選第二筆且可付款，不必取消第一筆。
- [ ] 透過「目前操作的報名」在兩筆間切換，核對編號、付款與報名狀態；重載後仍選同一筆。
- [ ] 取消或讓第二筆逾時，只改第二筆及相應名額、付款紀錄，第一筆仍已確認。選回已取消紀錄，所有狀態動作應停用。

## 不同票種摘要回驗

- [ ] 先送早鳥甲（NT$5,000），模擬付款並確認；只把表單改成學生票，未送出預覽應為 NT$4,500，已送出摘要仍是甲的早鳥票、NT$5,000、付款成功。
- [ ] 再送學生乙（NT$4,500），摘要應選中乙並顯示未付款；切回甲或重新整理後，姓名、ID、票種、金額與付款狀態都仍屬甲。
- [ ] 取消甲時保留甲的 NT$5,000 付款紀錄與未完成退款說明；乙仍維持 NT$4,500、未付款。

## 報名與候補聯絡驗證回驗

- [ ] 報名與額滿後的候補各填 abcde，核對 localStorage 中報名、付款、同意、通知、候補、名額與順位全不變；錯誤輸入留在欄位。
- [ ] Email、09 十碼與 +886 手機可各走合法流程；修正錯誤後只建立一筆，不重複扣名額。
