# EP16 驗收清單

## 逐項檢查

AI 產出後不要只看第一眼漂不漂亮，請依序檢查：

- [ ] 首頁第一屏說清楚服務適合誰、下一步是什麼。
- [ ] 資料欄位足以支撐核心流程，而非只留姓名電話。
- [ ] 票種有價格、名額、開賣與截止時間。
- [ ] 售完後進入候補，而非繼續顯示可報名。
- [ ] 付款逾時、取消、退款與報到狀態分得清楚。
- [ ] 通知含報名成功、付款提醒、活動前提醒、候補通知與異動通知。
- [ ] 個資同意把必要通知與行銷授權分開。
- [ ] 價格、限制、取消或隱私規則清楚。
- [ ] 手機版能完成主要行動，且文字與按鈕不重疊。

## 主動測試

本講是**最高風險、會扣到錢的票務站**，名額、候補、付款任一件靜默失敗，都是收錢沒位子或重複扣款的真實糾紛。最招牌的一測：把某票種名額調到剩 1 個，連送兩筆報名，看第二筆是被擋下轉候補，還是名額扣成 −1 照樣收。

記住：**AI 是被告不是法官，畫面才是證據**，它說「擋好了」不算數。

## 課堂定稿補充

### 招牌驗收：最後名額的占位測試

把票種名額調到剩一，用兩個獨立請求同時送出報名。預期一筆占位成功，另一筆不得占位。核對 TicketType 的名額、Registration 的報名與 WaitlistEntry 的候補紀錄，確認三份紀錄和畫面一致。占到名額仍可能是待付款。

### 把規格交給 AI，再親手驗收

把前面的需求整理成提示詞：活動資訊、票種、報名流程、候補規則、通知說明與八類資料欄位。JavaScript 負責選票種換總價等互動，CSS 是控制網頁排版的樣式。產出後先看票種的價格、名額、開賣與截止時間，再看售完後的新報名有沒有依規則進候補。付款逾時、取消或退款、報到各有紀錄，六種通知逐一核對，必要通知與行銷授權分開。最後縮窄畫面：平板改兩欄，手機改一欄，頁首上下排列，按鈕整排可點。程式裡的 media query，就是依畫面寬度切換樣式；max-width 是套用的寬度上限，程式的 px 就是像素，這裡用來計算網頁寬度；課本用一千零二十四個像素與六百四十個像素兩段。先核對看到的結果，再對照程式，發現缺口就請 AI 改那一點，修完重新操作一次。規格寫清楚，交給 AI 做，最後一定要自己親手點過一次。
