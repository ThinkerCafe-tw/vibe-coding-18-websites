EP16 施工規格

本規格整理自《網頁設計》第 16 講第 5.1 節的需求；是學員審閱與實作依據。

網站目標

活動資訊、票種、名額、報名表、通知與候補規則

使用者情境

使用者第一次進入網站時，需要在手機上快速判斷這個服務是否適合自己，並能完成主要行動：讓參與者理解活動資訊、票種、名額、付款與通知流程。

必要區塊

  1. Hero 首頁：名稱、定位、主張、主要行動按鈕
  2. 信任證據：真實照片、資歷、評論、規則或案例
  3. 活動資訊：日期、地點、議程、講者、適合對象
  4. 票種區塊：早鳥、一般、學生或 VIP 票種，顯示價格、名額、開賣與截止時間
  5. 報名流程：待付款、已付款、已確認、付款逾時、候補中
  6. 候補規則：名額釋出後保留多久，逾時如何往下一位遞補
  7. 通知說明：報名成功、付款提醒、活動前提醒、候補通知、異動通知
  8. 資料表單：姓名、聯絡方式、票種、個資同意、備註
  9. 規則說明：取消、退款、名額保留與隱私規則

資料欄位

請在頁面中示範下列資料結構：

  1. Event：活動名稱、日期、地點、主辦單位、活動狀態
  2. EventSession：場次、開始時間、結束時間、容量
  3. TicketType：票種名稱、價格、開賣時間、截止時間、名額
  4. Registration：報名人、票種、付款狀態、報到狀態
  5. PaymentRecord：金額、付款方式、付款結果、交易時間
  6. WaitlistEntry：候補順位、通知時間、保留期限
  7. NotificationLog：對象、內容、通道、發送狀態
  8. ConsentRecord：個資用途、同意時間、撤回方式

互動示意

請用少量 JavaScript示範：選擇不同票種會改變價格與剩餘名額；送出報名後先進入待付款；可以切換付款成功、付款逾時、取消與候補遞補狀態；每次狀態變更都要顯示對應通知。

設計要求

  1. 用清楚的 HTML結構與 CSS，建成一個可以直接打開的單一 index.html，CSS 寫在同一個檔案裡。
  2. 請使用 RWD，手機、平板、桌機都要可讀。
  3. 請避免假評價、假資歷、假價格或過度承諾。
  4. 表單與按鈕要有清楚的互動狀態，可以用靜態示意，不需要真的送出到伺服器。
  5. 畫面要清楚標示這是活動報名流程原型，尚未接正式金流、通知服務或後台資料庫。

課堂定稿補充

八張資料表，撐起從報名、付款到候補通知

本講八張資料表，依欄位與頁面模組一次看完。Event 記錄活動名稱、日期、地點、主辦單位與活動狀態，是對外活動主資料。EventSession 記場次、開始時間、結束時間與容量，管理多場次。TicketType 記票種名稱、價格、開賣時間、截止時間與名額，管理早鳥、一般、學生與貴賓，也就是 VIP 票種。Registration 記報名人、票種、付款狀態與報到狀態，追蹤一筆報名。PaymentRecord 記金額、付款方式、付款結果與交易時間，追蹤付款。WaitlistEntry 記候補順位、通知時間與保留期限，管理額滿後的遞補。NotificationLog 記對象、內容、通道、發送時間與是否送達，保存每次通知的紀錄。ConsentRecord 記個資用途、同意時間與撤回方式，管理個資與行銷授權。TicketType 同時撐起核心流程的名額，和規則說明的價格與限制。接著看兩條狀態機：票種狀態管這張票還能不能賣，報名狀態管這筆報名走到哪一步。

票種狀態機：售完不是終點，關閉才是

先看票種自己的狀態機，管的是這張票現在能不能賣。尚未開賣的票種，等到開賣時間到了就轉為報名中；報名中的票種，名額歸零就轉為售完，截止時間到或活動結束則轉為關閉。這裡最容易被忽略的一條邊，是售完可以回到報名中：有人退票或待付款逾時釋出名額時，票種可回到報名中；有候補時，先依順位保留給隊首，這條邊是可逆的；報名中與售完遇到截止時間或活動結束都會轉為關閉，關閉才是不再轉移的終態，也就是這條流程的終點。

報名狀態：付款逾時、取消／退款與報到

報名狀態管的是另一件事：這一筆報名走到哪一步，而不是這張票還剩不剩。待付款的報名可以轉成已付款或付款逾時；已付款的報名可以轉成已確認，或走向取消／退款；已確認可以轉已報到，也可依退票規則轉取消／退款，已報到轉已完成；付款逾時轉取消／退款；取消／退款與已完成都是終態，不會再轉移。候補不是這張票種的狀態，而是報名端 WaitlistEntry 這張表記錄的候補順位，兩條狀態機各管各的，不能混在一起看。退款與取消時，報名狀態、付款狀態、票種庫存必須一起更新。

狀態由後端改，前台顯示結果

剛才的箭頭，現在補上誰有權改。前台只送出報名、顯示結果，後端才依名額與時間更新票種。Webhook 是金流主動通知，驗簽用來確認通知不是假冒的，重送也只算一次；cron 是伺服器定時工作，檢查待付款逾時後依規則取消。釋出的名額先鎖定候補隊首，逾時才輪下一位。看畫面時，要能對回這些檢查與紀錄。

六種通知，是系統的一部分

活動網站要把通知當成系統的一部分，而不是最後才人工補寄。基本通知至少六種：報名成功在付款完成時觸發，內容是活動資訊、票種與報到方式；付款提醒在送出報名但未付款時觸發，內容是付款期限與取消規則；活動前提醒在活動前一到三天觸發，內容是時間、地點、交通與攜帶物；候補通知在名額釋出時觸發，內容是回覆期限與付款連結；異動通知在時間、地點或講師變更時觸發；課後資料在活動結束後發送。通知紀錄寫進 NotificationLog，記錄何時、用什麼通道、寄給誰、是否送達，是活動異動時能否說明責任的依據。正式上線要核對 Email、簡訊、LINE 的發送紀錄與失敗重送。

個資同意四層，行銷授權不能預設勾選

個資同意不能藏在一行小字裡，報名表應該把用途拆成四層：活動報名與聯絡是必要項目，沒有它就無法完成報名；活動前後通知也是必要項目，報到方式與臨時異動都要靠它送達；主辦方後續課程資訊是選填，跟這次報名沒有直接關係；合作夥伴行銷授權必須不預設勾選，而且要清楚列出對象或用途，這是最容易出問題、也是這一段要守住的底線。這樣使用者能看懂資料用途，並自行決定是否接受行銷。

六個後端判斷點，同步才不出事

名額、付款、候補與通知需要同步。這裡把交易邏輯拆成六個後端判斷點：票種庫存要回答這張票還能不能賣；待付款保留要回答報名未付款要保留多久；付款確認要回答誰能把狀態改成已付款；候補遞補要回答名額釋出後通知誰；通知紀錄要回答信有沒有發出去；退款與取消要回答取消後票種、付款與通知如何一起回復。六個判斷點共同維持票種、報名、付款、候補與通知的一致。

資料一致性規則

  • 固定教學時鐘為 2026/10/24 12:00（Asia/Taipei），顯示在票種與表單旁；開賣、截止、候補與通知使用同一個時鐘。
  • 時間早於開賣為「尚未開賣」，開賣至截止時間內為「報名中」，超過截止為「已截止」；開賣期間沒有名額則為「已售完」。票卡、選單與送出檢查共用規則。
  • 一般票 2026/11/01 09:00 開賣，因此此教學基準日不可選擇或送出；錯誤送出不建立報名、不扣名額。只有開賣期間額滿的早鳥票開放候補，截止後不遞補。

本頁資料與操作一致性

  • 取消與退款分開。未付款主動取消顯示已取消／未付款；保留逾時顯示已取消／未付款（保留逾時），不標成退款。
  • 付款成功後取消仍保留原付款成功紀錄、金額與交易時間；取消報名不代表完成退款，畫面明示尚未完成退款。本原型沒有完成退款按鈕。

多筆報名操作對象

  • 每筆報名使用獨立 ID，新增後選中該筆。狀態控制台提供報名選單，顯示姓名、票種、狀態與編號；付款、確認、逾時、取消均依同一選定 ID 取得報名及付款紀錄。
  • 選取已取消紀錄時只能查閱，不得再次付款或重複釋出名額；重載保留選取，舊版未保存選取 ID 的示例預設最近一筆。

EP16 驗收清單

逐項檢查

AI 產出後不要只看第一眼漂不漂亮，請依序檢查：

  • [ ] 首頁第一屏說清楚服務適合誰、下一步是什麼。
  • [ ] 資料欄位足以支撐核心流程，而非只留姓名電話。
  • [ ] 票種有價格、名額、開賣與截止時間。
  • [ ] 售完後進入候補，而非繼續顯示可報名。
  • [ ] 付款逾時、取消、退款與報到狀態分得清楚。
  • [ ] 通知含報名成功、付款提醒、活動前提醒、候補通知與異動通知。
  • [ ] 個資同意把必要通知與行銷授權分開。
  • [ ] 價格、限制、取消或隱私規則清楚。
  • [ ] 手機版能完成主要行動，且文字與按鈕不重疊。

主動測試

本講是最高風險、會扣到錢的票務站，名額、候補、付款任一件靜默失敗，都是收錢沒位子或重複扣款的真實糾紛。最招牌的一測：把某票種名額調到剩 1 個，連送兩筆報名，看第二筆是被擋下轉候補，還是名額扣成 −1 照樣收。

記住：AI 是被告不是法官，畫面才是證據，它說「擋好了」不算數。

課堂定稿補充

招牌驗收：最後名額的占位測試

把票種名額調到剩一，用兩個獨立請求同時送出報名。預期一筆占位成功，另一筆不得占位。核對 TicketType 的名額、Registration 的報名與 WaitlistEntry 的候補紀錄，確認三份紀錄和畫面一致。占到名額仍可能是待付款。

把規格交給 AI，再親手驗收

把前面的需求整理成提示詞：活動資訊、票種、報名流程、候補規則、通知說明與八類資料欄位。JavaScript 負責選票種換總價等互動，CSS 是控制網頁排版的樣式。產出後先看票種的價格、名額、開賣與截止時間，再看售完後的新報名有沒有依規則進候補。付款逾時、取消或退款、報到各有紀錄，六種通知逐一核對，必要通知與行銷授權分開。最後縮窄畫面：平板改兩欄，手機改一欄，頁首上下排列，按鈕整排可點。程式裡的 media query，就是依畫面寬度切換樣式；max-width 是套用的寬度上限，程式的 px 就是像素，這裡用來計算網頁寬度；課本用一千零二十四個像素與六百四十個像素兩段。先核對看到的結果，再對照程式，發現缺口就請 AI 改那一點，修完重新操作一次。規格寫清楚，交給 AI 做，最後一定要自己親手點過一次。

資料一致性主動回驗

  • [ ] 基準日的一般票應標示尚未開賣，票卡與選單停用；嘗試送出仍不建立報名，剩餘保持 12。
  • [ ] 早鳥最後一名送出後才扣成 0、顯示已售完並開放候補；測試開賣前、開賣當刻、截止當刻與截止後的狀態邊界。

多筆資料與操作一致性回驗

  • [ ] 分別做未付款取消、保留逾時與付款後取消；前兩者沒有退款紀錄，已付款取消保留原收款明細與時間，重新整理仍一致。

多筆報名狀態回驗

  • [ ] 第一位選學生票，完成付款及確認；不重設再新增第二位，控制台應自動選第二筆且可付款，不必取消第一筆。
  • [ ] 透過「目前操作的報名」在兩筆間切換，核對編號、付款與報名狀態；重載後仍選同一筆。
  • [ ] 取消或讓第二筆逾時，只改第二筆及相應名額、付款紀錄，第一筆仍已確認。選回已取消紀錄，所有狀態動作應停用。
