# EP03 驗收清單

## 逐項檢查

AI 產出後，先做五種檢查。

第一，檢查內容是否真實。刪掉 AI 自動編出來的評價、品牌合作、獎項與客戶名稱。

第二，檢查 HTML 結構。至少要能看到 `header`、`main`、多個 `section`、`footer`，作品集不要全部塞在沒有意義的單一大區塊裡。

第三，檢查 CSS 是否包含手機版規則。media query（媒體查詢）是 CSS 的條件式語法，意思是「當螢幕寬度小於某個值時，套用另一組版面規則」，響應式設計（RWD）就靠它切換欄數，寫法如下：

```css
.gallery { display: grid; grid-template-columns: repeat(3, 1fr); }  /* 桌機三欄 */
@media (max-width: 768px) {
  .gallery { grid-template-columns: 1fr; }  /* 寬度小於斷點 768px 時改單欄 */
}
```

手機版 RWD 的詳細做法沿用第 2 講，這裡只需搜尋 `@media`，確認 AI 是否有針對小螢幕調整欄位、圖片與按鈕。若沒有，請 AI 補上：

```text
請補上手機版 RWD 規則。桌機作品集維持三欄，平板兩欄，手機單欄。表單欄位在手機上全部改成單欄，按鈕高度至少 44px。
```

第四，檢查圖片路徑。若 HTML 寫的是：

```html
<img src="images/wedding-01.jpg" alt="台中戶外婚紗作品">
```

那你的 GitHub repository 裡就必須真的有：

```text
images/wedding-01.jpg
```

圖片路徑錯誤是部署後最常見的失敗之一：本機正常，不代表上線後正常。大小寫、資料夾名稱、副檔名都要一致。

第五，檢查 SEO 標籤。`title`（網頁標題）是瀏覽器分頁與搜尋結果第一行的文字，`meta description`（網頁描述）是搜尋結果標題下方那段說明，兩者都是 Google 判讀網站的依據。在 `index.html` 裡搜尋 `<title>` 與 `<meta name="description"`，確認有寫到攝影師名稱、服務類型與地區（例如 `<title>小柯攝影工作室｜台中婚紗婚禮紀錄</title>`）；若沒有或內容空泛，就請 AI 補上。

## 主動測試

這一講會讓客人**填詢問表單**，填完不會卡住、不扣錢，最容易出的是「沉默失敗」——看起來能寄的表單其實沒寄出去。最招牌的一撞，就是把表單**全空白直接送、Email 亂填**，看它擋不擋、送出後有沒有一句確認。

記住一句：**AI 是被告不是法官，畫面才是證據。** 問寫網站的 AI「表單會寄出去嗎？」它幾乎一定回「沒問題」，但會不會寄、有沒有編造、圖片連不連得上，都由畫面說了算。

逐項測試動作（抓編造、撞表單、撞圖片、撞分享）的完整清單，見書末〈附錄：主動測試卡〉。


## 多筆資料與操作一致性回驗

- [ ] 逐張對照目前照片與 alt；主體、動作與場景一致，換圖時同步修正替代文字與下載套件。

## 必填文字邊界回驗

- [ ] 逐一把姓名、拍攝地點填成三個半形空格（其餘必填合法）再送出，應保留表單並指出錯誤，紀錄與名額不變；全形空格與空字串也要攔阻。
- [ ] 改成正常資料後可送出一次。姓名使用「  測試 王  」時，保存或摘要應為「測試 王」，保留中間空格；其他欄位須符合各自格式。

## 成功後再次編輯回驗

- [ ] 先用合法資料送出並看到確認，再修改姓名或聯絡欄位，上一筆成功提示應立即消失。
- [ ] 逐一測試半形空格、全形空格、空字串、撤回必要同意與重設表單；未通過時不能留下成功提示，既有編號、紀錄內容與名額不得因此改變。
- [ ] 若有日期、時段、班級或模式按鈕，改選也應撤回舊確認。修正資料後可建立新的確認；原本已有編號的本頁紀錄仍可查閱。
